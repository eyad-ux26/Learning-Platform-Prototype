# Skillbench prototype: working rules

Stakeholder prototype for Phase 1. Frontend only: no backend, auth, billing, analytics service or AI API. Do not connect production services or start full Phase 1 work without explicit approval.

## Product rules (do not break)
- A path completes **only** when every required skill is Mastered. Lesson views and attempted activities never complete a path or create evidence.
- Mastery (provisional, `DEFAULT_MASTERY_RULE`): criteria met in ≥2 distinct `contextKey`s, ≥1 independent (no hints, no revealed solution).
- Duplicate responses (same activity, version, canonical hash) are recorded but add no evidence. Revealed solution → practice-only. Hints → evidence but not independent.
- Mastery is never revoked; later failures stay in history and flag practice.
- Recommendations come only from the curated bank; target the gap in a different context; say honestly when variants are exhausted.
- Critique scoring needs verdict **and** reason; every criterion needs ≥1 acceptable element. Free-text notes are stored, never assessed.
- No invented research, citations, endorsements or AI confidence scores in learner-facing claims. Uncertain learning claims go in `reviewNotes`.
- Preview paths must be labelled "not included in this prototype" and never look fully playable.
- Pricing is placeholder; payments, roles and access are simulations and must say so.

## Implementation decisions
- Domain logic lives in `src/domain` and stays React-free and deterministic. Unit tests are in `tests/`.
- Persistence goes through `PrototypeRepository` (`src/persistence`). Screens never touch localStorage directly.
- State is loaded client-side after mount (no hydration mismatch). Invalid stored data is backed up and reset; a seed fingerprint resets stale content.
- Learners see published versions only. Enrollments pin a version, attempts record theirs, and publishing never re-evaluates old attempts.
- Publication is gated by `validateBundle` (references and ≥2 contexts per required skill for `availability: "full"`).
- Seeded learner progress is generated by running canned responses through the real engine (`src/content/seed.ts`).
- Design Bench previews render behaviour tokens (`Behaviour` in `types.ts`); new Design Bench content reuses the shared `ProposalPreview`.
- Localisation (English + Arabic RTL, in Modern Standard and Egyptian variants): English is the stored language and Arabic is applied at display time. Use `useI18n()` (`tr` for UI text, `L` for content/domain messages); evaluate and submit with `view.rawBundle`, never the localised `view.bundle`. Fields that hold ids or machine values must be listed in `MACHINE_KEYS` (`src/i18n/core.ts`) so they are never translated. New learner-facing text needs an Arabic entry in `src/i18n/ar/` and an Egyptian one in `src/i18n/eg/` (see `docs/localisation.md`; `tests/i18n-coverage.test.ts` guards content). Admin and /demo stay English.
- UI strings go in `src/i18n/en.ts`; use logical CSS properties (`ms-`, `pe-`, `start-`) for future RTL.
- Visual identity is "Canvas Mode": a design-tool canvas (dot grid, mono frame name tags, selection handles, key caps). Fonts are self-hosted Bricolage Grotesque (headings, via `h1`/`h2` and `font-display`), Geist (UI) and Geist Mono (labels, numbers). Violet = brand and selection; skills get hues by position via `SkillRing`. Sound cues live in `src/components/sfx.ts` and follow `preferences.sound`.
- Activities share one "one question at a time" pattern: Brief (chat) · Decide (progressive tiles/cards with key caps) · Live (the product screen, with the part the current question is about highlighted via `.hl` handles and a name tag). Decision choices carry `affects` (hotspot ids of the node screen + tags) so the preview shows what an option touches; Design Bench highlights the region of the current decision (`activeDimension`); Critique highlights the selected element. Ship reviews show element / decision tickets that select the highlighted part. Below `lg` (phones first) the working view is a fixed-height app screen in `Workspace`: compact top bar, Brief/Live tabs, the interface scrolling in the middle (the highlighted part is scrolled into view), and a dock with only the current question. Controls use `DockLayout` (`src/activities/dock.tsx`): a step-chip row, the question and options scrolling inside the dock, and a pinned footer with the one primary action (Next / Decide / Submit). Choosing collapses the dock to a summary so the interface gets the screen; moving on reopens it. The page itself never scrolls while working.
- Home (HQ) and the path Board follow `Main`/`Board` in the Canvas design: toolbar with streak, Rep and rank ring; "Next brief" hero; daily goal; Reopened card; Specialisms cards with 46px skill rings; Career ladder; path hero with white skill-ring cards; 4-column board with a selected-brief detail and Field notes. Rep, streak, rank and the daily goal come from `src/domain/progression.ts`, derived from the learner's own attempts/evidence, labelled as prototype scoring, and never affect skill status or path completion.
- Charts use the dataviz-validated palette noted in `src/app/admin/page.tsx`; status is never conveyed by colour alone.
